# Governance Engine Runtime — Architecture

**Status:** PLANNING ONLY. No source, test, CI, workflow, or governance file was created or
modified. Nothing below is implemented.

**One tension named up front, not silently resolved:** `GOVERNANCE_VERTICAL_SLICE_TEMPLATE.md`'s
own closing rule states *"resist generalizing any part of this into a shared framework until at
least 2–3 more rules have been implemented this same way."* This document is exactly that
generalization, commissioned after only one rule (`REVIEW-3`). That instruction is not violated
by *designing* the runtime on paper — only by *implementing* it prematurely, which this document
does not do. But the design below is necessarily drawn from a sample size of one, and every
section says so where it matters. **This document's own recommendation is that it be treated as
a draft, re-validated once Governance Rules #2 and #3 exist, not adopted as final architecture
today.**

**Revision 1 (Architecture Review remediation):** §5 below now states explicitly that
`Validator`'s scope excludes per-execution evidence sanity-checking, resolving a BLOCKER finding
from the formal Architecture Review of `GOVERNANCE_RUNTIME_LIFECYCLE.md`. No other change in this
document.

---

## 1. Rule Definition Format

`GOVERNANCE_ENGINE_DESIGN.md`'s own table columns, already used for all 25 rules, are the format
— this section formalizes what already exists informally into one structured file per rule,
matching this repository's own `Machine Context` YAML-block convention (used throughout
`02_AI_CONTEXT/`), not a new format:

```yaml
rule_id: REVIEW-3
category: review                      # one of the 8 categories, §10
title: "Post-push verification"
status: implemented                   # designed | implemented | active | deprecated
version: 1
current_manual_process: "..."
desired_automated_verification: "..."
execution_points: [command, dogfood]  # subset of §19's contract; NOT the full 6-point list from
                                       # GOVERNANCE_ENGINE_DESIGN.md until composition (§11) wires
                                       # this rule into /verify, /review, /freeze, etc.
script: app/scripts/verifyPushState.ts
command_adapter: .claude/commands/ci-review.md
inputs: ["git HEAD", "origin ref", "GitHub Actions API"]
outputs: ["pass/fail per check", "masked-step flags"]
failure_behavior: block               # block | warn | flag  (§14)
rollback_behavior: revert             # revert | override | data-undo  (§7)
dependencies: []                      # other rule_ids or infrastructure this rule needs first
complexity: low
value: high
priority: highest
introduced: "Engineering Platform, slice 1, commit be88ecd"
deprecated: null
deprecated_reason: null
superseded_by: null
```

## 2. Rule Registry

One directory, one file per rule, mirroring the already-existing `app/.memory/` and
`PROJECT_KNOWLEDGE_SYSTEM` index-file convention (`module-index.md`, `decision-index.md`) rather
than inventing a new indexing pattern: `PROJECT_KNOWLEDGE_SYSTEM/05_ENGINEERING_PLATFORM/
governance-rules/<RULE-ID>.md`, each holding the §1 metadata block. A `REGISTRY.md` at that
directory's root is either hand-maintained (viable at 25 rules) or generated by scanning the
directory (worth building only once rule count makes hand-maintenance genuinely burdensome —
not assumed necessary yet, at n=1 implemented rules). The registry answers: "which rules exist,"
"what's each one's status," "which rules belong to category X," "which rules run at execution
point Y."

---

## 3. Rule Lifecycle

`designed → implemented → active → deprecated`. Evidenced today: 24 of the 25 rules in
`GOVERNANCE_ENGINE_DESIGN.md` sit at `designed`; `REVIEW-3` alone has moved through
`implemented` (script + adapter exist, passed the Vertical Slice Template's checklist) to
`active` (dogfooded successfully against a real, in-flight CI run). No rule has yet reached
`deprecated` — §17 designs that transition speculatively, from principle rather than precedent.

---

## 4. Rule Execution Pipeline

`trigger → load rule definition → run script → capture CheckResult[] → classify (pass / fail /
warn / masked-ambiguous) → route to failure behavior (§14) → report (§6)`.

**This pipeline is not new — it already exists, once, inside `verifyPushState.ts`.** The
script's own internal shape (an array of `CheckResult`-returning functions, aggregated into one
verdict, printed, translated into an exit code) *is* this pipeline's reference implementation.
The runtime's job is recognizing this shape as the standard every future rule's script follows,
not inventing a different one.

---

## 5. Rule Validation Pipeline

Distinct from *executing* a rule (§4): validating that a rule's *definition* is well-formed and
its implementation actually matches what the definition claims. This is
`GOVERNANCE_VERTICAL_SLICE_TEMPLATE.md`'s §6 Required Review Checklist, mechanized where
possible: does the declared `script` path exist and run standalone? Does the `command_adapter`
file contain any logic beyond "invoke the script and relay output" (a grep-based heuristic, not
a perfect check)? Do the declared `execution_points` actually correspond to where the rule is
wired in? **Notable, honest recursion:** this validation pipeline is itself best expressed as a
future governance rule (a rule that checks other rules) — not built now, named here as a
candidate for a later slice, not this document.

**Scope boundary (Architecture Review remediation):** this pipeline, and the `Validator` object
that performs it, validate a `RuleDefinition`'s well-formedness only — never the `Evidence`
gathered during a normal rule execution. Per-execution evidence sanity-checking is a distinct,
currently-undefined future capability, not implemented, out of current runtime scope — it is not
this pipeline under a different name, and building it is not authorized by this section.

---

## 6. Rule Reporting Pipeline

Today: console output only (`verifyPushState.ts` prints directly). The runtime's designed
extension: results also feed a durable, queryable log — this is exactly
`ENGINEERING_EVOLUTION_ROADMAP.md`'s Phase F2 (review-history log), not a new destination. A
rule execution's `CheckResult[]` becomes one entry in that log, giving every future `/audit` or
`/review` invocation a real history to query instead of only ever seeing the most recent run's
console output.

---

## 7. Rule Rollback Pipeline

Dispatches on the `rollback_behavior` metadata field (§1), generalizing
`GOVERNANCE_VERTICAL_SLICE_TEMPLATE.md`'s §8:

- `revert` → `git revert <rule's implementation commit>`. `REVIEW-3`'s actual category.
- `override` → the rule's block must ship with an explicit, logged override path (not a full
  revert, which would remove the check for everyone) — required for any future rule with
  `failure_behavior: block` that isn't purely advisory.
- `data-undo` → the rule's own mutation needs its own, separate undo — reverting the rule's code
  does not undo data it already wrote (e.g. a future auto-backfill rule touching
  `KNOWN_RISKS.md`).

No rule implemented so far needs `override` or `data-undo` — both are speculative until a
blocking or mutating rule is actually built.

---

## 8. Rule Dependencies

A directed graph, `rule_id → depends_on: [rule_ids | infrastructure_ids]`. Already evidenced in
`GOVERNANCE_ENGINE_DESIGN.md`'s own prose (`ARCH-1` explicitly "gated on A7", the not-yet-built
structured frozen-path list). The runtime formalizes this into queryable data so "what can I
implement next" is a graph traversal (find undependency-blocked, highest-priority rules) instead
of re-reading the whole design document's Implementation Order section by eye each time.

---

## 9. Rule Priorities

Already exists as data — `complexity`/`value`/`priority` in every rule's §1 metadata, sourced
directly from `GOVERNANCE_ENGINE_DESIGN.md`'s existing table. The runtime treats the
Implementation Order section's ranking as the *initial* priority values, not a fixed sequence —
once the registry (§2) and dependency graph (§8) exist, "next highest-ROI unblocked rule" becomes
a live query, not a static, hand-authored ordering that goes stale the moment a rule's status
changes.

---

## 10. Rule Categories

The 8 already established: Repository, Architecture, ADR, Decision Budget, Documentation, CI,
Review, Release. Treated as a closed enum in the rule definition format (§1) — a new category
would itself be a runtime-design decision, not something a rule author adds ad hoc.

---

## 11. Rule Composition

**Deliberately out of this runtime's scope, and stated as a boundary, not an oversight.**
Composing multiple atomic rules into a named, multi-step sequence (e.g. a future `/freeze`
running `REVIEW-3` + `REVIEW-2` + others) is `ENGINEERING_PLATFORM_BLUEPRINT.md`'s Layer 5
(Workflow Platform) responsibility, sitting *above* this runtime, not duplicated inside it. The
Governance Engine Runtime executes one rule at a time, correctly and reusably; Workflow Platform
decides which rules run together and in what order. This boundary is worth stating explicitly
because it is exactly the kind of duplicated-governance risk this whole platform exists to avoid
— a composition mechanism built twice, once here and once in Workflow Platform, would itself
become the next `app/.memory/project-status.md`-shaped drift risk.

---

## 12. Rule Inheritance (evaluated, not recommended)

**Should not be built.** No evidence across the 25 designed rules supports a class-hierarchy
("base rule extended by subclasses") pattern — every real case of shared logic found so far
(`REPO-1/2/5`'s shared staged-files-diff mechanism, `ADR-1`+`BUDGET-1/2`'s shared evaluation) is
**composition of a shared mechanism**, not inheritance of a base rule's behavior. Composition is
already covered structurally by §4's shared script-pipeline shape and the "extract reusable
pieces into a shared module" plan (see the REVIEW-3 extraction section below). Building an
inheritance system on top of that would add real complexity (a resolution order, an override
semantics) to solve a problem this platform doesn't actually have yet — a candidate for this
document's own "should never be implemented" list unless a future rule genuinely needs true
behavioral subclassing, which nothing so far does.

---

## 13. Rule Conflict Resolution

**Speculative — no real conflict has been observed (n=1 implemented rule).** Proposed default,
pending validation: the most restrictive verdict wins (`block` > `warn` > `flag`) when two rules
disagree about the same change, with an explicit human-override always available regardless of
which rule triggered the block — consistent with this whole platform's standing "no judgment
call made silently" principle. **This section should be revisited, not trusted, once at least
two rules with genuinely overlapping triggers exist** — today's design has nothing real to test
it against.

---

## 14. Rule Failure Handling

Generalizes `failure_behavior` (§1) into effect on the current workflow step, not just the
rule's own output:

- `block` → halt the current step; it may not be declared complete until the rule passes or is
  explicitly overridden (per §7's `override` rollback path). `REVIEW-3`'s own command adapter
  already states this in prose ("stop and report... before proceeding with anything else") —
  the runtime formalizes what is currently a instruction inside one markdown file into a
  general contract every rule's adapter should state the same way.
- `warn` → surface the result, continue the current step, but ensure it reaches the reporting
  pipeline (§6) so it isn't lost.
- `flag` → log for a later `/review`, never interrupts current work — appropriate for
  judgment-heavy rules (`DOC-1`, `ARCH-3`) where a false block would cost more than a missed
  catch.

---

## 15. Rule Metadata

Fully specified by §1's schema — restated here only to confirm every field has a defined
purpose: `rule_id` (registry key), `category` (§10), `status` (§3), `version` (§16),
`complexity`/`value`/`priority` (§9), `dependencies` (§8), `execution_points` (§19),
`script`/`command_adapter` (file locations), `failure_behavior` (§14), `rollback_behavior` (§7),
`introduced`/`deprecated`/`deprecated_reason`/`superseded_by` (§17).

---

## 16. Rule Versioning

A simple integer, bumped only when a script's logic changes in a way that could alter its
verdict on previously-passing input (not for comments, not for output-formatting changes) —
deliberately lighter-weight than full semver, matching this project's own existing lightweight
versioning conventions elsewhere (Prisma migrations are timestamp-ordered, not semver;
`PROJECT_KNOWLEDGE_SYSTEM` uses simple `v1.0`/`v1.1` tags). No rule has needed a version bump
yet — `REVIEW-3` ships at `version: 1`.

---

## 17. Rule Deprecation

A rule moves to `deprecated` with a required `deprecated_reason` and optional `superseded_by`,
but its definition file and script are **never deleted** — the same "archive before overwrite,
never lose the past" discipline `MILESTONE_HISTORY.md`'s own archival rule already establishes
for milestones, reused here rather than inventing a different retention policy for rules.
Deprecation candidates are genuinely rare: a rule about a tool/process no longer in use, or a
rule fully absorbed into a broader one. Policy rules like `CI-4` ("flip to blocking only on a
confirmed zero-error baseline") do **not** deprecate once satisfied once — they remain standing
policy, re-checked every time the situation recurs, not a one-time action to retire.

---

## 18. Rule Testing Strategy

Given every implemented rule's script talks to live git state and a live external API (GitHub
Actions), heavy mocking is deliberately avoided — the same reasoning this project already
applies elsewhere (preferring real `TEST_DATABASE_URL`-gated integration tests over fully-mocked
Prisma tests, preferring real smoke tests over synthetic ones at X.9.1). Proposed strategy:

1. **Dry-run support for any future blocking rule** — a script flag (e.g. `--dry-run`) reporting
   what it *would* block without actually blocking, so a blocking rule can be safety-tested
   before its `failure_behavior` goes live. `REVIEW-3` needs no dry-run mode since it never
   blocks anything by design (it's advisory/reporting only).
2. **Periodic re-verification via dogfooding**, not a synthetic unit-test suite — re-run each
   active rule's script against current real state as part of `/audit` (once that command
   exists), the same pattern `GOVERNANCE_VERTICAL_SLICE_TEMPLATE.md`'s §4 already mandates at
   implementation time, just recurring rather than one-time.
3. **A required non-vacuous verification at implementation time** (already mandated by the
   Template) remains the primary quality gate — this runtime does not add a parallel, separate
   test-authoring burden on top of it.

---

## 19. Rule Execution API

A minimal, uniform contract every rule script already informally satisfies (`verifyPushState.ts`
is the reference), formalized rather than changed:

- **Exit code**: `0` = every check passed; non-zero = at least one check failed. Already true.
- **Human-readable console output**: the default, already true — every `CheckResult` printed
  with a clear PASS/FAIL marker and detail.
- **Machine-readable output** (`--json` flag emitting the `CheckResult[]` array as JSON):
  **not built, not needed yet** — nothing currently consumes a rule's output programmatically.
  Add this only once Workflow Platform (§11's boundary) or the reporting pipeline (§6) actually
  needs to parse a rule's result rather than a human reading console text. Speculative addition,
  not a current requirement.

## REVIEW-3 Pieces That Become Runtime Components

Concrete extraction plan — which parts of `verifyPushState.ts`'s ~180 lines stop being
hand-written per rule and become shared runtime infrastructure:

| Existing REVIEW-3 code | Becomes | Reused by |
|---|---|---|
| `CheckResult` interface | The runtime's standard result type (§4) | Every future rule's script |
| `sh()` helper | A shared shell-exec utility | Any rule needing a git/CLI command |
| `repoRoot()`, `currentBranch()`, `ownerRepoFromRemote()` | A shared environment-detection module | Any rule needing repository context (nearly all of them) |
| `pollWorkflowRun()`'s generic retry/interval/max-attempts loop shape | A shared "poll until condition" utility | Any rule waiting on an async external result (e.g. a future `REVIEW-2` rerun-and-compare flow) |
| `findMaskedStepNames()` (workflow-file `continue-on-error` parsing) | A shared CI-workflow-introspection utility | Any future CI-category rule (`CI-3`, `CI-4`) |
| `main()`'s aggregate-verdict-then-exit-code shape | The runtime's standard script entry-point scaffold | Every future rule's script |
| The specific check functions (`checkHeadMatchesOrigin`, `checkWorkingTreeClean`) | **Stay rule-specific** — not extracted, since they *are* `REVIEW-3`'s actual logic, not infrastructure | Nobody — this is the part every future rule writes fresh |

## Estimated Impact

**Every figure below is derived from one data point (`REVIEW-3`) and stated as a directional
estimate, not a measured result — to be revisited once rules #2 and #3 provide real comparison
data.**

- **Percentage of future governance code eliminated:** roughly **50–60%** of a typical future
  rule's script, by line count. Basis: of `verifyPushState.ts`'s ~180 lines, the extraction
  table above accounts for the shell helper, environment-detection, polling loop, and
  entry-point scaffold — collectively closer to 100–110 lines — leaving roughly 70–80 lines of
  actual rule-specific check logic a future rule author would still write. A rule with no
  polling/CI-interaction need (e.g. a future frozen-path check) would see an even higher
  elimination percentage, since it wouldn't need `pollWorkflowRun`/`findMaskedStepNames` at all.
- **Expected reduction in duplicated code:** high specifically for the CI-polling and
  workflow-introspection pieces — without extraction, every future CI-category rule
  (`CI-3`, `CI-4`) and the flake-protocol rule (`REVIEW-2`, which needs a similar rerun-and-wait
  shape) would otherwise re-derive the same retry-loop logic from scratch, as happened once
  already (this session hand-wrote a GitHub Actions polling loop four separate times before
  `REVIEW-3` finally made it reusable).
- **Expected reduction in duplicated documentation:** moderate, roughly **40–50%** of the
  written prose per slice. The pre-/post-implementation disclosure's structural fields (files,
  complexity, budget-fit boilerplate) are already just restating the rule's own §1 metadata —
  once the registry exists, that restatement could be generated from the metadata rather than
  hand-typed each time, leaving only the "why" narrative (which cannot and should not be
  templated) to be written fresh.
- **Expected reduction in review effort:** partial, roughly **30–40%** of review time,
  concentrated entirely in the mechanically-checkable parts of §20's authoring checklist (does
  the adapter avoid duplicated logic, does the script exit cleanly, does `tsc -b` pass) once §5's
  validation pipeline exists. The judgment-heavy review (is this the right check, is the failure
  behavior correctly chosen) cannot be mechanized and should not be — no reduction claimed there,
  deliberately.
