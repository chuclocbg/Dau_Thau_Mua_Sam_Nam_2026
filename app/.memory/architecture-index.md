**Knowledge Platform immutable rules** (see `docs/knowledge-platform.md` for test-verified proof
of each): domain is always an open string, never an enum; new domains register via
`platform.registerProvider()` with zero platform/router/registry code changes; the router is a
pure `Map` lookup with no switch/if on domain names; `KnowledgeItem` is universal across every
domain; `KnowledgeRelationType` is `string`, not an enum — `KNOWLEDGE_RELATION_TYPES` is a
frozen object of well-known constants, not a restrictive union; `KnowledgeApplicabilityRule`
evaluation (`Retriever.resolveApplicableDocuments`) is identical for every domain.

**M0 is infrastructure config, not a `src/` module** — there is nothing to "freeze" in the
frozen-module sense (no TypeScript source, no repository interfaces). Its deliverables
(`docker-compose.yml`, `.env.template`, `.env.example` additions, `docs/infrastructure.md`) are
final for this phase but must be validated against a live Docker install before M1 is trusted.

**M1 architecture note — Prisma 7 driver adapters.** This schema/CLI combination
(`prisma@7.8.0`) removed the legacy `datasource.url` pattern; connection config now lives in
`prisma.config.ts`, and the runtime client requires an explicit driver adapter
(`@prisma/adapter-pg` + `pg`) passed to `new PrismaClient({ adapter })` — see
`src/persistence/prismaClient.ts` (the ONLY place `PrismaClient` is instantiated) and
`docs/prisma-production.md` for the full rationale, discovered by actually running `prisma init`/
`validate`/`generate` rather than assumed from memory.

**Notification provider architecture:** `NotificationProviderRegistry` is a pure
`Map<ChannelType, INotificationProvider>` lookup — application services depend only on
`ChannelType`, never on provider identity. 8 provider types documented
(smtp, microsoft_graph, sms_gateway, zalo_oa, fcm, web_push, internal_message_center,
government_notification_gateway); only `MockNotificationProvider` (tests) and
`InAppNotificationProvider` (real, in-process) are implemented in Phase L. Adding any other
provider is a new class + one `registry.register()` call — zero application-layer changes.

1. Frozen modules: never touch `src/legal/`, `src/masterdata/`, `src/procurement/workflow/`, `src/procurement/rules/`, `src/procurement/application/`, `src/procurement/package/`, `src/procurement/planning/`, `src/approval/`, `src/contract/`, `src/acceptance/`, `src/shared/financial/`, `src/shared/repository/`, `src/payment/`, `src/auth/` (FROZEN Phase J, 2026-07-04), `src/storage/` (FROZEN Phase K, 2026-07-05), `src/notification/` (FROZEN Phase L, 2026-07-05), `src/knowledge/platform/`, `src/knowledge/graph/`, `src/knowledge/search/`, `src/knowledge/repositories/`, `src/knowledge/application/`, `src/knowledge/providers/baseProvider.ts`, `src/knowledge/providers/legal/`, `src/knowledge/providers/procurement/` (Knowledge Platform CORE, FROZEN Phase N Stage 1-2, 2026-07-05 — the 14 remaining `src/knowledge/providers/*/` directories are NOT frozen, they don't exist yet)

   Note: `src/knowledge/knowledgeBase.ts` and `src/knowledge/knowledgeTypes.ts` are a separate,
   unrelated pre-existing module (Phase 16 Governance Knowledge Base) — not part of this list,
   not touched by Phase N.

   **Phase M1 extended every frozen module with a NEW `prisma*Repositories.ts` file
   implementing that module's existing repository interfaces — never modifying the frozen
   interface files or the frozen `memory*Repositories.ts` files themselves.** Payment
   (`src/payment/prismaPaymentRepositories.ts`) is the clearest example: a brand-new file, zero
   changes to `paymentRepository.ts`. `src/persistence/` (new, shared, not itself a frozen
   module) holds `prismaClient.ts` (the one PrismaClient singleton) and `decimalMapping.ts`
   (`mapPrismaRow()` — Decimal→number and DateTime→string conversion, reused by all 11 modules).
2. New module → new `*Integration.ts` bridge → never modify frozen files
3. No circular imports at any layer
4. Repository interfaces only in domain layer; Prisma only in infrastructure
